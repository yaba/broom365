Exchange distribution lists

read when you analyse

Distribution lists, mail-enabled security groups and dynamic lists, read from Exchange Online in one call. No owner comes straight from the inventory. To know whether a list is used, check it below: Broom365 counts its members and asks message trace whether any mail was addressed to it in the last 89 days (the longest history Exchange keeps). A list with no mail that is also empty or ownerless, and that no transport rule mentions, is flagged as likely unused. A list can still be used where Broom365 does not look (shared mailbox and calendar permissions, membership of other lists, SharePoint), and synced lists must be changed in on-premises AD.

{% elif tab == 'mailboxes' %}

Shared, room and equipment mailboxes

{% if mailboxes.available %}read {{ mailboxes.read_at[:10] }}: {{ mailboxes.count }} mailboxes{% else %}not read yet{% endif %}

These accounts have no password to sign in with, so they are not stale users; what matters is whether anyone still uses the mailbox. Check a mailbox below: Broom365 reads its last sign-in, who has Full Access or Send As (accounts that are deleted or disabled are called out), and asks message trace whether any mail arrived in the last 89 days. A shared mailbox that nobody can open, or that has had no sign-in and no mail, is flagged. It can still be used where Broom365 does not look (an app sending as it, forwarding rules), so every finding is a candidate for review.

{% elif tab == 'rules' %}

Exchange mail flow (transport) rules

read when you analyse

Rules that are disabled, expired, only auditing (not enforcing), or that name an address of this tenant which matches no distribution list, mailbox, user alias or group (dead reference). The last one needs the mailbox list to have been read (Shared mailboxes tab) and cannot see mail contacts or public folders, so confirm it in Exchange before acting. Nothing here proves a rule is unused: Exchange does not report how often a rule matched.

{% elif tab == 'members' %}

Internal users

read when you analyse

Ordinary (non-guest) accounts that cost money or linger unused. Disabled with licences: the account cannot be used but still holds paid licences. Stale: an enabled account with no sign-in for a long time (or created long ago and never signed in); MEDIUM when it holds a paid licence. Free licences (Power Automate free, Power BI free...) do not count as spend. Accounts synced from on-premises AD must be changed there. Service and shared accounts may not sign in interactively, so review before acting. Privileged accounts are on the Users tab. The threshold is in Settings.

{% if mailboxes.available %}Exchange mailbox types read: {{ mailboxes.count }} shared, room and equipment mailboxes ({{ mailboxes.read_at[:10] }}), so disabled accounts that are mailboxes by design are not reported.{% else %}Disabled accounts without a licence are not reported yet: shared, room and equipment mailboxes are disabled by design, and only Exchange can tell them apart from leftovers.{% endif %}

{% elif tab == 'guests' %}

External (guest) users

read when you analyse

People from other organisations who were invited. Stale guests have not signed in for a long time (or were added long ago and never signed in); pending ones never accepted the invitation. They keep an access path into the tenant, so they are candidates for review. A disabled guest is already inert (LOW). Search by name, e-mail or the guest's company domain to clean up a whole partner at once. Thresholds are in Settings.

{% elif tab == 'scripts' %}

Intune scripts and remediations

read when you analyse

PowerShell scripts, macOS shell scripts and Remediations. A script is flagged when it is unassigned, targets only empty groups, has never succeeded, is an assigned remediation that has gone idle, or is old. Old + any of the others is LIKELY_OBSOLETE_SCRIPT. Unassigned, old and empty-target come straight from the inventory; failing and idle need the run results, which you read below for the scripts you choose. Thresholds are in Settings; the groups they target also count as "used" on each group page.

{% elif tab == 'updates' %}

Windows update policies

evaluated when you analyse

Update rings, feature update profiles, expedite (quality) profiles and driver update profiles of Intune, with what each one sets and who it reaches. A policy is flagged when it is assigned to nobody or only to empty groups, when it overlaps another policy of the same kind (a device in both gets two sets of settings), when a ring sets no deadline (Microsoft recommends deadlines), when a ring pauses updates (a pause ends after 35 days), when the Windows version of a feature profile is out of support or about to be, when a driver profile waits for manual approval, or when an expedite profile is old. Update rings made with the Settings catalog and Windows Autopatch groups are not read yet, and devices are not looked at: this is about the policies. The groups they target also count as "used" on each group page. Thresholds are in Settings.

{% elif tab == 'intune' %}

Intune apps

evaluated when you analyse

Two kinds of cleanup candidates. Uninstall-only apps have only uninstall assignments and no required/available one: they are no longer deployed, only removed. Unassigned apps are deployed to nobody; once you check an app's relations below, apps that another app depends on are left out, and an old version superseded by a newer app is called out (deleting it removes the supersedence link). Exclusions are ignored. Uninstall-only apps appear straight from the inventory.
